# Go-to-market plan

## Launch objective

Earn developer trust and prove recurring operational use before optimizing paid conversion. The primary activation event is a user inspecting a real trace; the retention event is traces from the same project in three separate weeks.

## Audience and offer

| Segment | Message | Offer |
|---|---|---|
| Individual agent developer | Diagnose failures in minutes | Open local runtime |
| AI engineering team | One view across tools/frameworks | Cloud design-partner pilot |
| Platform team | Portable contract and controlled data path | Collector and deployment workshop |
| Security leader | Local defaults and governed capture | Threat-model and deployment review |

## Launch phases

### Public source release candidate

Open the Apache-2.0 repository with explicit release-candidate evidence and limitations. Recruit 10 design partners from teams actively debugging multi-framework Python agents. Conduct observed onboarding, weekly interviews, and issue triage. Do not paywall. Publish compatibility, privacy, benchmark, and schema evidence.

Exit: 4/5 users get a first trace in five minutes; five projects return weekly; two adapter needs repeat across accounts.

### Product beta

Ship signed npm packages, quick-start video, framework recipes, architecture explainer, public roadmap, contribution guide, and benchmark methodology. Launch through developer communities only after opt-in activation measurement and support coverage exist.

Exit: 50 weekly active projects, 30% four-week project retention, median issue first response under one business day.

### Cloud beta and GA

Invite retained teams to hosted retention, sharing, and alerts. Use a time-boxed pilot with success criteria and pricing disclosed upfront. Convert only when the managed service saves operational work.

## Content system

- “Anatomy of an agent failure” technical teardown
- Framework adapter recipes using the same event schema
- Transparent performance and data-handling reports
- Incident-debugging examples with synthetic data
- OpenTelemetry interoperability guidance

Every asset drives one action: run the demo, instrument a workflow, or apply for a pilot.

## Community

Use GitHub Discussions for design proposals, issues for actionable work, and a public RFC process for schema changes. Label good first issues, define adapter ownership, publish a code of conduct and security policy, and recognize contributors in releases. Stars are reach, not product success.

Ask for sponsorship only through verified repository funding links. Explain that funding supports maintenance, compatibility, documentation, and security; it does not purchase schema control or preferential security fixes.

## Sales motion

Cloud is product-led for small teams. Larger organizations use founder/customer-engineer sales: qualify production volume, retention, privacy, deployment, identity, procurement, and success outcome. A pilot must have an executive sponsor, technical champion, baseline metric, end date, and conversion decision.

## Launch guardrails

Do not claim deterministic replay, broad framework support before maintained adapters exist, compliance certification before audit, or cost savings without measured baselines.
